# Research: Sitemap for Search Engine Discovery

## 1. Generation mechanism: build-time script vs. hand-written file

**Decision**: A pure JS function (`src/build/generateSitemap.js`) builds the URL list and XML string
from the same sources of truth the app already uses; a thin CLI script (`scripts/generate-sitemap.mjs`)
calls it and writes `public/sitemap.xml`. Wired in as an npm `prebuild` script, so `npm run build`
(already the exact command the GitHub Actions deploy workflow runs) always regenerates it immediately
before Vite copies `public/` into `dist/` — the same passthrough already relied on for
`public/.htaccess`, `public/robots.txt`, and `public/llms.txt`.

**Rationale**: Spec FR-004 requires the sitemap to need zero manual edits when a page or language is
added. `robots.txt` and `llms.txt` (feature 006) could be hand-written once because their content is
fixed prose; a sitemap's content is a list that grows with the site's actual page count (24 entries
today, and counting) — hand-maintaining that list would violate FR-004 the moment a sixth language is
added, and is exactly the kind of error-prone, easy-to-forget task automation exists to remove.
Deriving it from the same locale list (`useLocale.js`) and language-content directory
(`content/languages/*.md`) the running app itself reads guarantees the sitemap can never drift from
what the site actually serves.

**Alternatives considered**:
- *Hand-written, like `robots.txt`/`llms.txt`*: Rejected — those files' content doesn't scale with the
  page count; a sitemap's does, and FR-004 explicitly rules out manual per-entry maintenance.
  documented in [002-responsive-sidebar-search](../002-responsive-sidebar-search)/[003-i18n-language-detection](../003-i18n-language-detection).
- *Generate at request time via a server route*: Rejected — the site is a static SPA with no
  server-side runtime (Apache + `.htaccess` rewrite only); introducing one just for this would be a
  large, unjustified architecture change for a file that only needs to be correct at deploy time.
- *A Vite plugin instead of a `prebuild` npm script*: Considered equivalent in effect, but a plain
  Node script is simpler, has no Vite-plugin-API surface to learn or maintain, and is trivially
  unit-testable as a plain function — preferred per the Constitution's Code Quality principle
  (no unjustified complexity).

## 2. Should `public/sitemap.xml` be committed to git?

**Decision**: No — add `public/sitemap.xml` to `.gitignore`, alongside `dist/`. It is regenerated by
the `prebuild` step on every build (local or CI), the same way `dist/` itself is a build output.

**Rationale**: `robots.txt` and `llms.txt` are committed because a human wrote and reviews their prose
content. The sitemap's content is 100% derived from other already-committed sources (`useLocale.js`,
`router/index.js`, `content/languages/*.md`) — committing the generated output as well would create a
second, redundant source of truth that could silently go stale between commits (e.g., if someone adds
a language file but forgets to re-run the generator before committing), which is the exact failure
mode FR-004 exists to prevent. Treating it as a build artifact (like `dist/`) makes staleness
structurally impossible instead of relying on developer discipline.

**Alternatives considered**:
- *Commit it and regenerate/verify in CI*: Rejected — adds a "did you forget to regenerate?" CI check
  for no benefit over simply never committing a derived file.

## 3. URL set and page inventory

**Decision**: Enumerate the same three route kinds already declared in `src/router/index.js` — home
(`/:locale`), history (`/:locale/history`), about (`/:locale/about`) — crossed with the three locales
in `SUPPORTED_CODES` (`src/composables/useLocale.js`), plus one `language-detail` entry
(`/:locale/languages/:slug`) per `.md` file under `content/languages/`, crossed with the same three
locales. Slugs are derived by lowercasing the filename and stripping `.md` — identical to
`slugFromFilename()` in `src/content/parseLanguageFile.js` — so a new language file picked up by
`useLanguages.js` at runtime is automatically picked up by the sitemap generator too.

**Rationale**: Reusing the router's own route list and the language directory (rather than a
separately maintained page registry) is the only way to satisfy FR-004 and SC-004 (zero manual edits
for a new page).

## 4. Cross-language alternates format

**Decision**: Each `<url>` entry includes one `<xhtml:link rel="alternate" hreflang="...">` per
supported locale (matching the `hreflang` codes already used, `pt-BR`/`en`/`es`) plus one
`hreflang="x-default"` pointing at the English (`en`) version — using the `xmlns:xhtml` namespace on
`<urlset>`, the sitemap protocol's standard mechanism for declaring language alternates
(sitemaps.org's hreflang extension, also documented by Google's own sitemap guidelines).

**Rationale**: This is the sitemap-level equivalent of the `<link rel="alternate" hreflang="...">` tags
`useLocaleSeoTags()` already injects into `<head>` per page (`src/composables/useLocaleSeoTags.js`),
including the same `x-default → en` convention. Reusing an identical convention avoids sending
crawlers conflicting signals between the sitemap and the page's own head tags.

**Alternatives considered**:
- *Separate per-language sitemap files with a sitemap index*: Rejected — massive overkill at 24
  entries; a sitemap index exists to solve the 50,000-URL/50MB single-file limit, which this site is
  nowhere close to.

## 5. `lastmod`, `priority`, `changefreq`

**Decision**: Omit all three from every `<url>` entry.

**Rationale**: `priority` and `changefreq` are explicitly and publicly disregarded by Google's crawler
(confirmed in Google's own Search Central sitemap documentation) and add no practical value — matching
spec's documented assumption. `lastmod` is technically useful when accurate, but computing a truthful
value here would require reading each page's git history or content-file mtime at generation time,
adding real complexity (a new build-time dependency on git plumbing) to reproduce a freshness signal
that isn't required for the file to be valid or effective, and that this site's content doesn't change
often enough to make measurably useful. Per the Constitution's Performance principle (no speculative
complexity without a demonstrated need), it's left out; it can be added later if a concrete need
appears.

## 6. `robots.txt` update

**Decision**: Append a single `Sitemap: https://helloworld.valdir.dev.br/sitemap.xml` line to the
existing hand-written `public/robots.txt` (created in `006-pagespeed-report-fixes`).

**Rationale**: This satisfies spec FR-005/User Story 2 using the exact mechanism the sitemap protocol
itself recommends (a `Sitemap:` directive in `robots.txt`) and the same discovery pattern this project
already established for `llms.txt` (linked from nowhere else — but a sitemap specifically has a
standard robots.txt-based discovery slot, unlike `llms.txt`, so it's used here). `robots.txt`'s content
is otherwise unaffected — `006`'s research decision to omit a `Sitemap:` directive is superseded now
that a sitemap actually exists.

## 7. Testing approach

**Decision**: Two levels, mirroring `006-pagespeed-report-fixes`'s pattern:
1. A Vitest unit test (`tests/unit/generateSitemap.spec.js`) calls `generateSitemap()` directly with
   the real `SUPPORTED_CODES` and real `content/languages/*.md` slugs, and asserts: entry count
   matches `(page kinds × locales) + (language slugs × locales)`, every `<loc>` is a well-formed
   absolute URL under the site's origin, every entry has one alternate per locale plus `x-default`,
   and no `<priority>`/`<changefreq>`/`<lastmod>` tags are present.
2. A Playwright e2e assertion added to the existing `tests/e2e/static-files.spec.js` (from `006`)
   requests `/robots.txt` and asserts it contains the new `Sitemap:` line with the correct absolute
   URL.

**Rationale**: The generator only runs at build time (via `prebuild`), not in the Vite dev server, so
an e2e test can't request `/sitemap.xml` from `localhost:5173` the way `006`'s tests request
`/robots.txt`/`/llms.txt` (those are committed static files present from the start). Testing the pure
function directly is both simpler and stronger: it exercises the real logic without needing a build
step in the test run, consistent with the Constitution's Testing Standards principle (happy path +
known edge cases, deterministic, fast). The build's actual file output is still verified manually via
`npm run build && ls dist/sitemap.xml` in `quickstart.md`, matching `006`'s precedent.
